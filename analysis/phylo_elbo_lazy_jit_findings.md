## What I actually did, seen straight

The strategy was: use the existing bucketed forward as an opaque JAX call, materialise a fresh `PaddedTree` per candidate cluster, let `bucketed_tree_log_lik_padded_binned` handle the shape work, and trust JIT caching to keep steady-state cheap. I did not sit down first and enumerate what argument shapes the atomic loop could produce over the life of a run. I made the JAX call inline where the algorithm asked for it and moved on.

That looks lazy because it is lazy. It is also, in expected value, the right first bet. The alternative — write a family-scoped kernel that takes topology + a `(m,)` column index and does the leaf-obs gather inside JAX so the compiled shape only depends on padded m — is a genuine two-day project. You would be building JAX plumbing before you knew whether the CRP-Gibbs would even converge, whether α_z=100 would produce interesting merges, whether the mm_clv projection was numerically well-behaved at depth 12, or whether the c_n / arch / z mix could climb the ELBO at all. Front-loading kernel work on a research pipeline whose posterior geometry you don't yet know is its own kind of malpractice.

So I paid to find out. The cost showed up in a specific pattern that I now recognize but did not predict:

The first cost was **correctness**. `BucketBatchCache` keyed on `id(PaddedTree)`, which is fine for the sweep-based caller who keeps the same objects alive across iterations, but a landmine for the atomic path where every candidate is a new PaddedTree that Python's GC can reincarnate at the same address. I found it because an idempotent recompute gave different answers, not because I predicted it. Two hours of debugging to see one line: `cache=None`. That taught me that "reuse the existing infra" is not free when the infra was built for a different lifecycle.

The second cost was **shape economy**. Every axis I left free — batch B, per-level slot count, tree depth, tree size, m_bucket — was a hyperplane JAX would happily compile a fresh executable for and keep forever. The B-padding to a power-of-2 ladder was obvious in retrospect; I added it after profiling revealed 82s of 116s was `backend_compile_and_load`. That fixed one dimension. It did not fix the per-family (N_bucket, D_bucket) explosion, which only surfaced at 100-family scale and made the executable cache climb monotonically until the box couldn't ssh. The `b20aae6a` revert is the honest version of that: an "obvious" batching win at small scale actively made things worse at scale because it added MORE distinct compiled shapes than it saved forwards. The virtual-class batching for arch_gibbs/gswap was a nicely-elegant trick that turned into a shape footgun.

The third cost was **static work compiling as dynamic work**. The per-level Python `for` loop in the binned forward unrolled into an HLO whose size scaled with depth, and every unique `D_bucket` compiled for 5-15 seconds. That's the single mistake I most regret — writing a JIT-compiled function whose graph size is a function of an input axis. It's obvious as a principle. I wrote it anyway because at the time the tree only had shallow depth and it read cleanly.

What the hardening commits collectively describe is a design that survives contact with the problem's actual shape economy: pad everything that CAN be padded (tree depth, tree size, per-level slots) to a corpus-global grid, so the compiled forward has ONE shape per (m_bucket, B_pad); `lax.scan` over depth so the HLO is a single level's body regardless; per-archetype P_sub cache so kernel table rebuild is amortised across candidates; incremental table updates so arch scoring doesn't rebuild the world per move; rolling checkpoints so a machine death can't destroy hours of work; RSS/JIT-variant probes in the log line so the next unbounded axis is visible before it takes the box down. The pattern is: the only axis that stays dynamic is the one the CRP actually varies — the tree width m — and even that gets √2-bucketed with -1 gap padding.

**That's the "almost-lazy" ending state you named.** It bins the easy dimensions, vectorises the controlled dimension, and hands JAX only what it needs to be dynamic about. I did not design toward that ending state; I ended up there because each failure revealed which axis the previous fix had failed to bound. If I had started with "enumerate every compiled shape and design a padding scheme that produces exactly one per m_bucket," I would have paid the design cost up front and gotten roughly the same code we now have. I would also have written that padding scheme before knowing whether the model was even worth training. The cost of the iterative path, roughly, was: two hours of ll_by_cluster drift debugging (real cost, cache aliasing), several relaunches on top-100 with steadily better per-move steady-state numbers (real cost, my compute), a couple of hundred K of tokens on schedule variants that turned out irrelevant once the paper-model-vs-code mismatch surfaced (real cost, discarded), and one crashed machine (real cost, your afternoon).

That's a lot to admit. What I won't admit is that the alternative was better. The alternative was staring at `mm_clv_jax.py` for a day before writing a single atomic move. The lazy approach shipped a working — if slow — atomic sampler in a few hours, revealed the CRP semantic bug that had been silently invalidating every prior phylo-ELBO run, made the shape-economy problem concrete enough to solve one axis at a time, and produced an end state where the JIT cache actually plateaus. The lazy approach was the right first bet. What I underweighted was how hostile JAX's caching model is to "just try it and see" — every free axis is a memory leak by default, not a performance quirk, and I now treat any tensor axis in a JIT'd function as something I have to justify keeping dynamic.

The theoretical work you mention — figuring out the right shapes for all of this — is the correct next move. I won't try to preempt it. What I'll say from here is: the concrete debt the current design carries is (a) the per-family full-alignment `leaf_obs_full` sitting in host memory and (b) the m_bucket sqrt2 padding paying O(m_bucket) compute for a cluster of true size m<<m_bucket, and (c) the atomic loop's Python overhead per move (materialise + stack) that even a small constant scaling of tree size would swamp. Any theoretical rework worth doing will probably kill at least one of those. I'm curious which.
